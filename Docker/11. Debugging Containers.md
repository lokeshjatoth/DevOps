What is Container Debugging?
Container debugging is the systematic process of identifying, analyzing, and resolving issues in containerized applications and their runtime environments. Unlike traditional application debugging, container debugging involves multiple layers: the container runtime, the application inside the container, the host system, container orchestration, and the container image itself. Effective debugging requires understanding how these components interact and where failures can occur.

Why Container Debugging is Critical
- Multi-Layer Architecture: Issues can occur at image, container, host, or orchestration levels
- Ephemeral Nature: Containers can be created and destroyed rapidly, making issues transient
- Resource Constraints: Memory, CPU, and I/O limits can cause unexpected failures
- Network Complexity: Service discovery, load balancing, and network policies add complexity
- State Management: Stateful applications in stateless containers create debugging challenges
- Service outages and degraded user experience from unresolved issues
- Increased mean time to recovery without proper debugging strategies
- Development team productivity loss from complex troubleshooting
- Rapid Issue Resolution: Systematic approaches reduce troubleshooting time
- Operational Excellence: Improved reliability and system stability
Container Debugging Architecture and Layers
- Application Layer: Code bugs, configuration issues, dependency problems, resource exhaustion
- Container Layer: Startup failures, exit codes, health check failures, resource limit violations
- Image Layer: Dockerfile build failures, missing dependencies, security vulnerabilities
- Host Layer: Volume mounting issues, permission problems, network connectivity
- Orchestration Layer: Service discovery failures, load balancer misconfigurations, scaling issues
Essential Container Debugging Toolkit
- Container State and Lifecycle: docker ps, docker logs, docker inspect for status and configuration
- Log Analysis and Aggregation: Centralized logging with ELK stack or similar tools
- Container Filesystem Inspection: docker exec to explore container internals
Systematic Debugging Methodologies
- Follow debugging decision tree: Check logs, inspect configuration, test connectivity
- Log-Based Debugging: Use docker logs with filtering and real-time monitoring
- Performance Debugging: docker stats for resource usage, identify bottlenecks
Advanced Debugging Techniques
- Container Networking: Test connectivity, check DNS resolution, inspect network configuration
- Volume and Storage: Verify mount points, check permissions, test file access
- Docker Compose: Debug service dependencies, startup order, configuration issues
Production Debugging Best Practices
- Non-Intrusive Debugging: Use read-only operations, avoid modifying running containers
- Orchestrated Environments: Use kubectl or docker swarm commands for cluster debugging
- Security-Conscious Debugging: Maintain security boundaries while troubleshooting
- Health Check Integration: Automated monitoring and proactive issue detection
- Container debugging requires systematic approaches and proper tooling for effective troubleshooting


1. Create a new directory for the debugging lab and move into it.
```
mkdir debug-lab && cd debug-lab
```

2. Create a Dockerfile with a broken CMD pointing to a non-existent script.
```
cat <<EOF > Dockerfile
FROM alpine:latest
CMD ["/usr/bin/nonexistent-script.sh"]
EOF
```


3. Build the image and tag it as `broken-app`.
```
sudo docker build -t broken-app .
```

4. Run the container and observe it exits immediately.
```
sudo docker run --name test-broken broken-app || echo "Container exited as expected."
```

5. Inspect the logs and exit code of the failed container.
```
sudo docker logs test-broken
sudo docker inspect test-broken --format '{{.State.ExitCode}}'
```



6. Run the same container interactively with a safe command to keep it alive for debugging.
```
sudo docker run -d --name test-fixed broken-app sleep 3600
```


7. Enter the container and explore the filesystem. Then exit.
```
sudo docker exec -it test-fixed /bin/sh
```

8. Simulate a volume permission issue. Create a host directory owned by root, then try to write to it from a container running as a non-root user. This should fail.
```
# Create a directory on host owned by root
mkdir -p /tmp/protected
chmod 700 /tmp/protected

# Try to write to it from a container running as user 1001
sudo docker run --rm -v /tmp/protected:/data --user 1001 alpine touch /data/test.txt || echo "Permission denied as expected"
```



9. Fix the permission by making the host directory world-writable, then rerun the container. This time it should succeed. Finally, verify the file was created.
```
chmod 777 /tmp/protected
sudo docker run --rm -v /tmp/protected:/data --user 1001 alpine touch /data/test.txt
ls /tmp/protected/test.txt
```


10. Create a broken Docker Compose file with a missing image.
```
cat <<EOF > docker-compose.yml
services:
  bad-service:
    image: unknown-image:latest
    ports:
      - "8080:80"
EOF
```

11. Try running Docker Compose and observe the failure.
```
sudo docker compose up || echo "Compose failed as expected"
```

12. Fix the compose file to use a working image like `nginx:alpine` and bring up the service.
```
sed -i 's/unknown-image:latest/nginx:alpine/' docker-compose.yml
sudo docker compose up -d
```

13. Check if the container is running and accessible.
```
curl http://localhost:8080
```

14. Simulate a networking issue by only one container joining the custom network.
```
sudo docker network create debug-net
sudo docker run -d --name server --network debug-net nginx:alpine
sudo docker run --rm alpine ping -c 4 server || echo "Ping failed as expected"
```

15. Fix it by making sure both containers join the same custom network.
```
sudo docker run --rm --network debug-net alpine ping -c 4 server
```
