Why Container Security Matters
- Shared Kernel: All containers share the host OS kernel, creating potential attack vectors

- Image Vulnerabilities: Malicious or vulnerable code in base images affects all derived containers

- Privilege Escalation: Improper container configuration can lead to host system compromise

- Supply Chain Attacks: Compromised images from public registries can introduce malware

- Runtime Attacks: Running processes inside containers can be exploited to break out

- Data breaches and intellectual property theft from security vulnerabilities

- Compliance violations (GDPR, HIPAA, SOX) and regulatory fines

- Service disruptions and downtime from security incidents

- Reputational damage and customer loss

Core Security Principles
- Principle of Least Privilege: Grant containers only minimum permissions needed to function

- Run as non-root user whenever possible

- Drop unnecessary Linux capabilities

- Use minimal base images (Alpine, Distroless, Scratch)

- Restrict network access and port exposure

- Defense in Depth: Implement multiple layers of security controls

- Build Time: Secure base images, vulnerability scanning

- Runtime: Resource limits, network policies, monitoring

- Immutable Infrastructure: Treat containers as immutable, replaceable components

- Read-only filesystems prevent runtime modifications

- Configuration through environment variables and secrets

Docker Security Features and Controls
- User Namespaces: Map container users to different host users for isolation

- Linux Capabilities: Drop unnecessary capabilities like CAP_SYS_ADMIN

- Security Options: Use --security-opt for AppArmor, SELinux profiles

- Resource Constraints: Limit CPU, memory to prevent resource exhaustion attacks

Common Security Vulnerabilities
- Running as Root: Containers running as root user create security risks

- Overprivileged Containers: Using --privileged flag unnecessarily exposes host

- Secrets in Images: Storing secrets in image layers exposes them in history

- Vulnerable Base Images: Using outdated base images with known vulnerabilities

Security Best Practices
- Dockerfile Security: Use non-root users, minimal base images, multi-stage builds

- Runtime Security: Resource limits, read-only filesystems, network policies

- Image Vulnerability Scanning: Scan images for CVEs before deployment

- Runtime Security Monitoring: Monitor container behavior and network traffic

Incident Response and Forensics
- Isolate: Stop network traffic to/from compromised container

- Preserve: Create forensic image of container for analysis

- Analyze: Examine logs, processes, network connections

- Remediate: Replace with clean container image

- Learn: Update security policies and controls

- Use docker commit, docker save for forensic preservation

Common Security Misconfigurations
- Using --privileged flag unnecessarily allows container to access all host devices

- Mounting Docker socket into container gives control of entire Docker daemon

- Running containers with --network=host shares host network namespace

- Storing secrets in environment variables exposes them in process lists

- Using latest image tags in production creates unpredictable security updates

- Solutions include specific capabilities, Docker secrets, custom networks, pinned image tags

Compliance and Governance
- CIS Docker Benchmark: 100+ security recommendations for Docker

- NIST Cybersecurity Framework: Risk management approach for containers

- ISO 27001: Information security management standards

- SOC 2: Security and availability controls for service organizations

- Automated Compliance: Use tools like Docker Bench, Falco, Twistlock for continuous monitoring

- Container security requires ongoing vigilance and adherence to security best practices


1. First, run a standard ubuntu container and check who the current user is. You will see you are the root user.
```
sudo docker run --rm -it ubuntu whoami
```

2. Now, run the same container, but add the `--user` flag to run as a specific user ID (e.g., 1001). This user does not exist in `/etc/passwd`, but the container process will run with this UID.
```
sudo docker run --rm -it --user 1001 ubuntu id
```
3. Run an Nginx container with a read-only root filesystem. The container will start, but Nginx will fail because it needs to write to its log files and PID file.
```
sudo docker run -d --name readonly-test --read-only nginx
```
4. Check the logs of the `readonly-test` container to see the errors caused by the read-only filesystem.
```
sudo docker logs readonly-test
```

5. Run the Nginx container again with a read-only filesystem, but this time, also mount a writable temporary filesystem (`tmpfs`) for the paths Nginx needs to write to.
```
sudo docker run -d --name readonly-fixed --read-only --tmpfs /var/cache/nginx --tmpfs /var/run nginx
```

6. Verify that the `readonly-fixed` container is now running successfully.
```
sudo docker ps
```
